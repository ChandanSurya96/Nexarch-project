# Decisions (ADR Log)

**Purpose:** Every significant technical or product decision, recorded with its reasoning, alternatives considered, and consequences — so a future engineer (or founder revisiting a choice six months from now) doesn't have to reconstruct *why* from git blame. New entries go at the bottom; existing entries are never edited after the fact — a changed decision gets a new ADR that references the old one, the same way the schema itself only moves forward via new migrations (see [database.md](./database.md)).

---

### ADR-001 — Flask over FastAPI/Django for the backend
**Date:** 2026-07-14
**Decision:** Use Flask, as specified at founding.
**Reasoning:** Founding scope mandates it; also genuinely reasonable for this project's size — lightweight, flexible, well-understood.
**Alternatives considered:** FastAPI (async support, auto-generated OpenAPI docs out of the box), Django (batteries-included, admin panel).
**Consequences:** Nexarch loses FastAPI's automatic OpenAPI generation and native async, and Django's built-in admin — the admin gap in particular means any internal moderation/support tooling needs to be built deliberately rather than inherited for free. Mitigate by keeping [api.md](./api.md) rigorously up to date as the manual substitute for auto-generated docs, and treating an admin panel as an explicit Phase 1/2 backlog item, not an assumption.

### ADR-002 — Read-only broker sync only for MVP; no trade execution
**Date:** 2026-07-14
**Decision:** No order placement, no copy trading, until Phase 5 at the earliest.
**Reasoning:** Execution brings SEBI stockbroker/portfolio-manager-adjacent regulatory obligations that are an entirely different scope of legal and compliance work than read-only data aggregation. Staying read-only lets Nexarch validate the trust/discovery thesis (does anyone want this?) before taking on that cost.
**Alternatives considered:** Launching with copy-trading from day one, closer to the US app Dub's model (see [product/competitor-analysis.md](./product/competitor-analysis.md)) — rejected as premature given Dub itself operates under SEC/FINRA registration specifically to support that model.
**Consequences:** Monetization can't include brokerage/execution commission early; Phase 4's Creator Economy has to work on subscriptions/access rather than trade-copying revenue.

### ADR-003 — PostgreSQL as the primary datastore
**Date:** 2026-07-14
**Decision:** PostgreSQL, as specified at founding.
**Reasoning:** Relational integrity matters for financial holdings data; strong JSONB support covers the flexible fields (`sector_allocation`, `health_metrics`) without needing a second database; mature ecosystem on both Railway and AWS.
**Alternatives considered:** None seriously — this was a founding-scope decision, recorded here for completeness rather than genuine deliberation.
**Consequences:** None negative identified at this scale.

### ADR-004 — JWT auth with short-lived access token + rotating refresh token
**Date:** 2026-07-14
**Decision:** As detailed in [security.md](./security.md).
**Reasoning:** Standard, well-understood pattern for a decoupled SPA/API architecture; stateless access tokens scale horizontally without session storage.
**Alternatives considered:** Server-side session cookies only (simpler, but couples the API to sticky sessions or a shared session store, which fights the stateless-scaling goal in [architecture.md](./architecture.md)).
**Consequences:** Requires careful refresh-token storage (httpOnly cookie, not localStorage) to avoid reintroducing the XSS exposure JWTs are otherwise prone to.

### ADR-005 — Redis + Celery for background jobs and caching
**Date:** 2026-07-14
**Decision:** Add Redis and a Celery-based job queue, not specified in the founding brief but required by the architecture.
**Reasoning:** Broker sync involves slow, rate-limited, third-party network calls that cannot run inline on a request without harming API latency and reliability. A queue decouples sync throughput from API traffic.
**Alternatives considered:** RQ (simpler, smaller ecosystem than Celery) — worth reconsidering if Celery's operational overhead feels disproportionate to Phase 1's actual job volume; not a hill to die on either way.
**Consequences:** One more moving part to run and monitor in every environment, including local dev (mitigated via Docker Compose, see [development-guide.md](./development-guide.md)).

### ADR-006 — Single `portfolios` table with nullable owner FKs, not separate verified/public tables
**Date:** 2026-07-14
**Decision:** See full reasoning in [database.md](./database.md).
**Reasoning:** Avoids duplicating holdings/snapshot/strategy-tag relationships across two parallel table sets for data that's treated identically by every downstream consumer once loaded.
**Alternatives considered:** Separate `verified_portfolios` / `public_portfolios` tables.
**Consequences:** Requires an application-level (or DB check) constraint to prevent a portfolio having both a `user_id` and a `public_investor_id`, or neither.

### ADR-007 — No single "trust score"; objective health indicators only
**Date:** 2026-07-14
**Decision:** Portfolio Health surfaces multiple labeled, independently-explained indicators (diversification, concentration, age, consistency) rather than one composite number.
**Reasoning:** Directly follows from the founding philosophy in [vision.md](./vision.md); also a real regulatory consideration, not just a philosophical one — see [security.md](./security.md) on why a single score sits closer to "advice" than a set of transparent indicators.
**Alternatives considered:** A composite 0–100 "Nexarch Score," which several competitor/adjacent products in other markets do use — rejected specifically because it's the more common, more expected pattern, and Nexarch's differentiation depends on not doing the expected thing here.
**Consequences:** Slightly harder onboarding UX (users may initially expect and look for a single number) — worth deliberate design attention rather than treating it as a solved problem by omission.

### ADR-008 — True volatility/risk metrics deferred pending a market-data vendor
**Date:** 2026-07-14
**Decision:** Diversification and sector concentration ship in Phase 1 (computable from holdings alone); volatility and risk-adjusted metrics wait for Phase 2+.
**Reasoning:** Broker read-only sync provides current holdings, not historical price series. Computing genuine volatility needs a market-data source Nexarch doesn't have yet.
**Alternatives considered:** Approximating "risk" from sector concentration alone and labeling it as risk — rejected as misleading; a concentration proxy is not the same thing as volatility, and presenting it as such would be exactly the kind of fabricated-looking precision [product-requirements.md](./product-requirements.md) explicitly warns against.
**Consequences:** Phase 1 Portfolio Health is honestly incomplete on this dimension rather than falsely complete. Phase 2 needs a market-data vendor decision as its own follow-up ADR.

### ADR-009 — React Query (or SWR) for server state; no global client-state library
**Date:** 2026-07-14
**Decision:** Proposed default, not specified at founding — see [architecture.md](./architecture.md).
**Reasoning:** Nexarch's frontend state is overwhelmingly server data (portfolios, discovery feed, holdings) with caching/refetch needs React Query handles natively; local-only UI state (modal open/closed, form inputs) doesn't need a global store at this scale.
**Alternatives considered:** Redux/Zustand for everything — rejected as unnecessary complexity for Phase 1's actual state-management needs; revisit only if a concrete cross-cutting client-state need emerges.
**Consequences:** None identified; low-risk, easily reversible choice.

### ADR-010 — Evaluate Account Aggregator integration in parallel with the first direct broker integration
**Date:** 2026-07-14
**Decision:** Don't commit fully to broker-by-broker API integration as the only sync path before testing the AA framework in parallel. See full reasoning in [broker-integrations.md](./broker-integrations.md).
**Reasoning:** NSDL and CDSL are both now live, SEBI-specified FIPs on the RBI Account Aggregator network for securities holdings — a broker-agnostic, standardized, regulator-blessed consent path that sidesteps needing a separate integration (and separate commercial terms) per broker.
**Alternatives considered:** Direct broker API integration only, broker by broker, per the founding brief's literal broker list.
**Consequences:** Adds an FIU-registration/compliance evaluation to the Phase 1 workplan that wasn't in the original scope — worth the added upfront work given the downstream simplification if it pans out. Needs a founder decision on whether to pursue directly or through a TSP that already holds FIU status.

### ADR-011 — Public display of synced holdings is not yet cleared against broker data-vending terms
**Date:** 2026-07-14
**Decision:** Do not default new broker connections to public visibility until this is resolved; keep `is_public` opt-in and off by default regardless (this was already the plan per [product-requirements.md](./product-requirements.md), but this ADR records the specific reason it's now non-negotiable rather than just a sensible default).
**Reasoning:** Zerodha's Kite Connect terms describe the API as an execution platform, "not a data distribution service," and describe displaying/redistributing its data on external platforms as a violation of exchange data-vending policy. See [broker-integrations.md](./broker-integrations.md).
**Alternatives considered:** Proceeding without broker sign-off on the assumption that a user sharing their own data is obviously fine — rejected; "obviously fine" is exactly the kind of assumption that deserves a real answer before it's load-bearing for the product's core feature.
**Consequences:** A direct conversation with each broker (starting with Zerodha) is a pre-launch blocker for the *public-profile* feature specifically, even though it's not a blocker for building the private sync/verification architecture now.

### ADR-012 — Pilot broker set to Upstox; Account Aggregator evaluated in parallel, absent objection
**Date:** 2026-07-15
**Decision:** Treat Upstox-as-pilot-broker and AA-evaluated-in-parallel (per ADR-010) as the working plan for Phase 1.
**Reasoning:** Both were proposed with reasoning in prior discussion; neither drew an objection after being explicitly raised as open questions. Recorded here honestly as *proceeding absent objection*, not as an explicit founder sign-off — worth distinguishing from ADRs above that do reflect founder-confirmed direction, since this document's value depends on accurately recording how a decision was actually reached.
**Alternatives considered:** Continuing to hold both open pending explicit confirmation — rejected as unproductive; these are low-stakes, easily-reversed choices (an adapter swap and a spike, not an architectural commitment), unlike the actual gate on writing production code itself, which this ADR does not resolve.
**Consequences:** Phase 1 broker-adapter work can proceed against Upstox; the AA-integration spike is scheduled alongside it rather than deferred. Either can still be revisited cheaply if reconsidered later.

### ADR-013 — Sector/market-cap enrichment via a static seed reference, not a live data vendor
**Date:** 2026-07-25
**Decision:** Enrich synced holdings with sector/market-cap category from a small, checked-in `app/data/sector_mapping.py` dict keyed by ISIN, rather than any live data source.
**Reasoning:** Brokers don't reliably return sector or market-cap category in holdings responses (see [broker-integrations.md](./broker-integrations.md)), and no market-data vendor is selected yet (ADR-008 defers that decision to Phase 2). A small manually-curated seed unblocks Phase 1 Milestone 2's analytics without waiting on a vendor decision that's out of scope this early.
**Alternatives considered:** Waiting for the Phase 2 market-data vendor decision before shipping any sector-based analytics — rejected as blocking useful Phase 1 functionality (allocation, HHI concentration) on a Phase 2 dependency for no real benefit, since the enrichment step is cleanly swappable later. Guessing/interpolating sector for unmapped ISINs — rejected; unmapped ISINs get `sector=None`, never a guess, per the same "don't fabricate precision" reasoning as ADR-008.
**Consequences:** This is manual-curation debt, same in kind as the Public Investor Library's manual curation — it needs ongoing extension as real pilot users' holdings surface unmapped ISINs, and the seed entries themselves were compiled from general knowledge rather than an authoritative source, so they need verification against NSE/BSE's official ISIN master data before being relied on beyond local development (see the module docstring in `sector_mapping.py`).

### ADR-014 — Envelope encryption implemented with `cryptography.fernet`, KMS-backed key deferred
**Date:** 2026-07-25
**Decision:** Implement broker-token envelope encryption (a random data key per token, wrapped by a master key) using `cryptography.fernet`, with the master key sourced from `ENCRYPTION_KMS_KEY_ID` as a local stand-in for a real KMS.
**Reasoning:** [security.md](./security.md) requires envelope encryption for broker tokens — the highest-sensitivity data Nexarch holds — but no cloud KMS is provisioned yet, and standing one up is its own infrastructure decision, not something to block Milestone 2's broker-connection work on. Implementing the same envelope *shape* now (per-record data key, wrapped by a master secret) means swapping in a real KMS later is a two-function change (`_wrap_data_key` / `_unwrap_data_key` in `app/services/encryption_service.py`), not a re-architecture.
**Alternatives considered:** A single static application-wide encryption key with no envelope/per-record data-key structure — rejected; security.md explicitly calls this out as the thing envelope encryption avoids. Waiting to provision a real KMS before writing any broker-connection code — rejected as blocking Milestone 2 on an infrastructure decision that's cheap to retrofit later.
**Consequences:** This module is explicitly **not production-ready** as-is — a real KMS (AWS/GCP) must back the master key before real user broker tokens are stored, per security.md's own pre-launch checklist. This is a hard gate to track before Phase 1 goes live with real users, not a someday item.

**Design note (not a numbered decision — an honest limitation, logged for the same reason ADR-008 is):** `portfolio_age_days` (introduced in Milestone 2's analytics) is computed from the earliest `portfolio_snapshots` row for a portfolio — i.e., time since Nexarch started tracking it, not true holding-acquisition date. Broker holdings endpoints don't reliably expose purchase/acquisition dates, so this under-counts age for holdings a user held before connecting Nexarch (the exact case [product/user-journey.md](./product/user-journey.md) calls out for the Rohan persona). Revisit if a broker or the AA framework ever surfaces genuine acquisition-date data. Separately, "value" throughout Milestone 2's analytics (`total_value`, `sector_allocation` weighting) means `quantity * avg_cost_price` — cost basis, not live market value — for the same reason ADR-008 defers true volatility: no market-data vendor is selected yet, so there's no current-price source. Both limitations should be surfaced honestly in the UI when it's built, not silently presented as more precise than they are.

### ADR-015 — Portfolio activity is a computed diff over snapshot history, not a stored ledger
**Date:** 2026-07-25
**Decision:** `GET /api/v1/portfolios/:id/activity` (new in Milestone 3) is computed on read by diffing consecutive `portfolio_snapshots` rows — sector-allocation deltas, holding-count change, and a generated one-sentence summary. No new table.
**Reasoning:** Inspired by, but deliberately not copying, copy-trading apps' rebalance/activity feeds (Parrot Finance, Dub — see the system-design exploration earlier in this project's history). Nexarch has no transaction-level data — holdings are point-in-time per [database.md](./database.md) — so there's no "buy X / sell Y" event to record even if we wanted one; a diff between two known states is the only honest thing to show. Computing it on read reuses data Milestone 2's sync worker already writes, and keeps this feature reversible/cheap if it doesn't prove useful.
**Alternatives considered:** A stored `portfolio_activity` ledger table, written at sync time — rejected for now as unused schema surface area (per [database.md](./database.md)'s own "don't add tables before there's a writer for them" principle); revisit only if computing the diff on every read becomes a measured cost at real scale. Attributing a cause/rationale to each change (mirroring Dub's algorithmic "why" text) — rejected; Nexarch doesn't know why a holding changed, and inventing a plausible-sounding reason would be a fabrication, not a description.
**Consequences:** The feature is strictly descriptive — no "auto-copy synced" language, no comments, no attributed rationale — matching the same descriptive-only discipline as the Investor Strategy Overview feature ([security.md](./security.md)). It only shows activity once a portfolio has 2+ snapshots, which for Public Investor Library entries seeded from a single point-in-time disclosure means no activity is shown at all yet — honestly empty, not fabricated, consistent with ADR-008's reasoning.

**Design note (not a numbered decision):** the Public Investor Library seed data (`scripts/seed_public_investors.py`) deliberately leaves `Holding.avg_cost_price` blank for all seeded holdings. An initial attempt to back-derive a per-share price from each holding's publicly disclosed value-in-crores produced a number roughly 60x off from the real share price on a spot check (Vijay Kedia's Neuland Laboratories holding) — a concrete demonstration of exactly the "silently wrong precision" ADR-008 warns against. Consequence: Public Investor Library portfolios currently have no computed `sector_allocation`/health metrics at all (analytics_service's value math is `quantity * avg_cost_price`, which is 0 when cost price is blank) — `GET .../analytics` correctly returns the existing "no snapshot yet" honestly-empty shape for these portfolios. Revisit once there's a verified per-holding value source for these disclosures, not by guessing harder.

### ADR-016 — Browser API calls go through the Next.js rewrite proxy (relative paths), not the absolute backend URL
**Date:** 2026-07-25
**Decision:** `lib/api.ts`'s `apiFetch` always requests the relative path `/api/v1/...`; it never reads `NEXT_PUBLIC_API_BASE_URL` at request time. That env var is used only server-side, by `next.config.ts`'s `rewrites()`, to know where to proxy to.
**Reasoning:** `next.config.ts` already had a `rewrites()` block forwarding requests to the Flask backend, specifically to avoid CORS in development — but the pre-existing `apiFetch` defaulted to the *absolute* backend URL, bypassing that proxy entirely. Called from the browser, that's a cross-origin request carrying the httpOnly refresh cookie, and Flask has no CORS configuration (none exists in `apps/api` yet). Routing through the proxy keeps every browser request same-origin, so the cookie is sent without needing CORS set up on the backend at all.
**Alternatives considered:** Configuring `flask-cors` on the backend to accept the frontend's origin with credentials — rejected for now as a real but deployment-phase concern (per [security.md](./security.md)), not something Milestone 4a needs to solve just to develop against a co-located local backend.
**Consequences:** Manual verification of this fix caught a second, pre-existing bug in the rewrite itself: `source: "/api/:path*"` captured everything after `/api/`, then appended it to `NEXT_PUBLIC_API_BASE_URL` (which already ends in `/api/v1`) — producing a doubled path (`/api/v1/v1/auth/refresh`, a live 404) the moment something actually exercised the proxy for the first time. Fixed by pinning the rewrite's `source` to the versioned prefix (`/api/v1/:path*`) so the destination isn't double-appended. This is exactly the kind of bug that only surfaces under real browser traffic, not a type-check or a unit test — worth remembering before assuming a scaffolded-but-never-exercised piece of config is correct.

### ADR-017 — Access token lives in React state (and a synced in-memory module variable) only; never `localStorage`
**Date:** 2026-07-25
**Decision:** `AuthProvider` holds the signed-in user in React state and pushes the access token into `lib/api.ts` via `setAccessToken()`, an in-memory module variable `apiFetch` reads to set the `Authorization` header. The token is never written to `localStorage`, `sessionStorage`, or any other JS-readable persistent store.
**Reasoning:** Matches ADR-004/[security.md](./security.md)'s threat model directly — the entire point of the httpOnly refresh cookie is that XSS can't read a long-lived credential, and putting the (shorter-lived, but still bearer) access token in `localStorage` would reopen exactly that hole.
**Alternatives considered:** Storing the access token in `localStorage` for simplicity (survives a hard refresh with no extra code) — rejected; that's the specific pattern ADR-004 already rejected for the refresh token, and doing it for the access token would undermine the same threat model for a smaller convenience win.
**Consequences:** A hard refresh always loses the in-memory token, so the app needs a silent-refresh-on-load step (`AuthProvider`'s mount effect, calling `POST /auth/refresh`, which works because the httpOnly cookie survives the refresh) before it knows whether anyone's signed in — implemented and verified live (register → hard refresh → session restored without bouncing to `/login`).

### ADR-018 — Route protection is a client-side `<RequireAuth>` wrapper, not Next.js Middleware
**Date:** 2026-07-25
**Decision:** `components/RequireAuth.tsx` reads the same `useAuth()` state the rest of the app uses, shows a loading state while the silent refresh is in flight, and redirects to `/login` once loading finishes with no user. No Next.js Middleware is used for auth in this milestone.
**Reasoning:** Middleware runs at the edge and could check for the refresh cookie's *presence*, but not its validity, without calling the Flask backend anyway — mixing that into Middleware would duplicate the silent-refresh logic already in `AuthProvider` and wouldn't share the same React Query cache or auth context the rest of the app reads.
**Alternatives considered:** Next.js Middleware performing a lightweight cookie-presence check as a first-pass gate, with the client-side check as a second layer — rejected as unnecessary defense-in-depth for Milestone 4a's scope (no protected pages exist yet that render sensitive data server-side); worth reconsidering once a real protected page (e.g. the profile page in Milestone 4b) exists and the loading flash becomes an actual UX problem.
**Consequences:** Every protected page renders a brief loading state on first load while the silent refresh resolves — acceptable for now, revisit only if this becomes a measured UX issue at higher traffic.

### ADR-019 — `GET /api/v1/users/me/portfolio`, returning `data: null` (200) rather than 404 when none exists yet
**Date:** 2026-07-25
**Decision:** Add a small, additive endpoint so the frontend can discover the signed-in user's own portfolio id — every existing portfolio endpoint is keyed by `portfolio_id`, and there was no way to look that up otherwise. Returns the same `PortfolioSchema` shape used everywhere else; no new DTO.
**Reasoning:** `Portfolio` rows are created lazily, inside `sync_service.run_sync`, only after a broker connection's first successful sync — not at registration, and not even immediately at the OAuth callback (`handle_callback` only creates the `BrokerConnection`; the Celery task creates the `Portfolio` later, asynchronously). So a freshly-registered user, and even a user who just finished connecting a broker seconds ago, legitimately has zero `Portfolio` rows for a little while. Treating that as `data: null` rather than a 404 error follows the same "honest absence over fabricated precision" reasoning as ADR-008/ADR-015 — it's the expected state for every new signup, not a failure.
**Alternatives considered:** A 404 with a specific error code (`PORTFOLIO_NOT_YET_SYNCED`) the frontend would branch on — rejected as needless ceremony; a `null` data value is already a normal, well-understood "nothing here yet" signal elsewhere in this API (e.g. `strategy_overview: null`, `health: null` in the analytics response), so reusing that convention keeps the contract consistent rather than introducing a second way to say the same thing.
**Consequences:** Frontend code calling this endpoint must treat `null` as a legitimate, common response — not wrap it in error handling meant for actual failures.

### ADR-020 — Sync-pending state is handled by bounded client-side polling, not WebSockets/SSE
**Date:** 2026-07-25
**Decision:** After a successful broker callback, the frontend polls `GET /users/me/portfolio` every 3 seconds (via a plain `setTimeout`-driven refetch, not React Query's built-in `refetchInterval`, to keep the stop condition simple and directly testable) until it resolves non-null, or 40 attempts (~2 minutes) elapse — after which it shows a "taking longer than expected" message instead of polling forever.
**Reasoning:** No push infrastructure (WebSockets, SSE, a notifications service) exists anywhere in this codebase yet, and standing one up for this single "tell me when my first sync finishes" use case is disproportionate to Phase 1's actual traffic.
**Alternatives considered:** An unbounded interval that polls forever — rejected; if a sync silently fails in a way that never produces a `Portfolio` row (a bug, or a permanently failed connection), an indefinite poll just burns client resources without ever telling the user something's wrong. Bounding it surfaces that instead of hiding it.
**Consequences:** Revisit only if sync latency or scale make polling a real measured problem — e.g. if Phase 2's additional broker integrations make first-sync latency high enough that 2 minutes of polling routinely isn't enough.

### ADR-021 — Reconnecting a broker updates the existing `BrokerConnection` row in place, keyed by `(user_id, broker_name)`
**Date:** 2026-07-25
**Decision:** `broker_connection_service.handle_callback` now looks up an existing connection for the same user and broker before deciding whether to insert or update — found while building the frontend's "Reconnect" flow for an expired connection (product-requirements.md's Broker Connection acceptance criteria require this to work, not just show a prompt).
**Reasoning:** The prior implementation unconditionally inserted a new `BrokerConnection` row on every callback. Since a `Portfolio` links to exactly one `broker_connection_id` and is only created when `connection.portfolio is None` at sync time, a second row for the same user+broker would have no `Portfolio` linked yet — its first sync would then create a *second*, disconnected `Portfolio` for a user who already has one, silently splitting their holdings/snapshot history across two identities. This is a real data-integrity bug, not a hypothetical: it would have fired the first time any user's broker token expired and they reconnected.
**Alternatives considered:** Adding a unique constraint on `(user_id, broker_name)` and catching the resulting DB error — rejected as more moving parts than needed; an application-level lookup-then-update is simpler and reads more clearly at the one call site that matters.
**Consequences:** A new `reconnect` audit-log event type (distinct from `connect`) so the audit trail can tell the two cases apart — added to the documented `event_type` set in `database.md`. Regression-tested in `test_broker_connections.py`.

### ADR-022 — Add `portfolio_id` to `PublicInvestorSchema`
**Date:** 2026-07-25
**Decision:** `PublicInvestorSchema` (`app/schemas/public_investor.py`) now includes `portfolio_id`, resolved via `fields.Method` from the existing `PublicInvestor.portfolio` relationship. Found while building the frontend's Public Investor Library page (Milestone 4c).
**Reasoning:** The schema had no portfolio reference at all — `id, name, slug, bio, source_disclosure_url, last_disclosure_update` — even though every seeded entry has exactly one linked `Portfolio` (`portfolio_type='public'`). Viewing a library entry's actual holdings/allocation/health means navigating to the portfolio detail view, which needs that id. Same reasoning and shape as ADR-019: a small, additive field, not a new endpoint or a breaking rename.
**Alternatives considered:** Looking up the portfolio client-side via the Discovery Feed (which already returns portfolio `id` and includes Public Investor Library entries, since `discovery_service.list_investors` filters only on `is_public`, not `portfolio_type`) — rejected as an unnecessary indirection for a page whose whole point is the Public Investor Library specifically, and `DiscoveryInvestorSchema` doesn't carry `bio`/`source_disclosure_url`/`last_disclosure_update`, which the Library page needs to satisfy product-requirements.md's "every holding traces to a cited disclosure" requirement anyway.
**Consequences:** `public_investor_service.list_public_investors()`/`get_by_slug()` now eager-load the relationship (`selectinload(PublicInvestor.portfolio)`) to avoid N+1 — a small list today (5 seeded entries) but matches the eager-loading discipline already applied elsewhere in this codebase.

### ADR-024 — Resolve ADR-008 by reusing Upstox's own historical-candle API, not a separate market-data vendor
**Date:** 2026-07-25
**Decision:** Phase 2's first slice (Milestone 5) adds portfolio volatility — annualized standard deviation of daily log returns, value-weighted across holdings — computed from Upstox's own Historical Candle Data API (`GET /v3/historical-candle/{instrument_key}/days/1/{to_date}/{from_date}`, verified against Upstox's current developer docs), authenticated with the same broker access token already stored per `BrokerConnection`. `BrokerAdapter` gained `fetch_historical_prices`, implemented in `UpstoxAdapter`, wired into `sync_service.run_sync` alongside the existing holdings fetch.
**Reasoning:** ADR-008 deferred volatility specifically because "computing real volatility requires historical price series... which broker read-only sync doesn't provide," and logged the follow-up as "Phase 2 needs a market-data vendor decision." Upstox already has this data behind the exact OAuth token this codebase already manages end-to-end (encryption, refresh, expiry) — no new vendor relationship, no new credential type, no new consent flow.
**Alternatives considered:** A broker-agnostic market-data vendor (a paid or free-tier NSE/BSE data API, independent of any specific broker connection) — rejected for this slice. It would additionally cover Public Investor Library portfolios (which have no broker token at all), but introduces exactly the new vendor relationship/cost/credential-management surface ADR-008 was trying to avoid taking on lightly, for a benefit — 5 seeded profiles — that's small against reusing infrastructure already built, trusted, and audited. Revisit only if Public Investor Library analytics parity becomes an actual product priority, not preemptively.
**Consequences:** Volatility is only ever computed for verified (Upstox-connected) portfolios — Public Investor Library portfolios remain without it, same as their existing gap for every other health metric (ADR-015's design note, since seeded holdings have no `avg_cost_price`). `health.volatility` is `null` wherever it can't be honestly computed (no connection, too few price points, per-holding fetch failure) — never a fabricated or interpolated number, the same convention ADR-008 itself established. A per-holding historical-price fetch failure is isolated (try/except per holding in `sync_service._fetch_closes_by_holding_id`) so one bad ISIN doesn't fail the whole sync. No migration needed — `portfolio_snapshots.health_metrics` was already a flexible JSON column built for exactly this (see that model's own docstring).

### ADR-025 — `portfolio_snapshots` intentionally allows multiple rows per day; `created_at` is the deterministic ordering key
**Date:** 2026-07-25
**Decision:** Add `portfolio_snapshots.created_at` (server-generated UTC timestamp, migration `0004`) and use it as the mandatory secondary sort key everywhere "latest snapshot" or chronological snapshot order matters: `portfolio_service.get_latest_snapshot`/`get_snapshot_history` and `activity_service.get_activity`. `snapshot_date` stays exactly as it was — the business date a snapshot represents — and gets **no** uniqueness constraint.
**Reasoning:** Found while answering a direct question about whether volatility is immutable once stored. `run_sync` always inserts a new `PortfolioSnapshot` row (never updates one in place, by design — the table is meant to be append-only), but nothing stopped two syncs from landing on the same calendar date: a scheduled sync plus a manual "sync now," or two manual syncs 300+ seconds apart (the cooldown floor). `get_latest_snapshot` ordered by `snapshot_date DESC` alone; SQL gives no ordering guarantee among rows with an equal sort key, so which same-date row `/analytics` returned as "current" was genuinely undefined — it could differ between two identical requests. `id` (a random UUID4) can't substitute as a tiebreaker since it isn't chronologically sortable, which is why this needed a real new column rather than reusing an existing one.
**Alternatives considered:** A `UNIQUE(portfolio_id, snapshot_date)` constraint with upsert-on-conflict — rejected; explicitly out of scope for this fix (two same-day syncs are legitimate, independent events — an evening re-sync after intraday portfolio changes shouldn't silently discard the morning's snapshot) and it would break the append-only history model `portfolio_snapshots` is built on, which `/history` and `activity_service` both depend on. Using `id DESC` as the tiebreaker — rejected once confirmed `id` is a random `uuid.uuid4()`, not a sequential/time-sortable identifier, so it carries no chronological information.
**Consequences:** Every "give me the latest snapshot" query must sort by `(snapshot_date, created_at)`, never `snapshot_date` alone — a rule worth remembering for any future query added against this table, not just the three fixed here. Migration `0004` backfills existing rows' `created_at` to the migration's own run time (the only honest value available, since true creation time was never tracked before this) via a single `ADD COLUMN ... NOT NULL DEFAULT now()` statement — safe and backward compatible, no separate backfill step needed. The existing `(portfolio_id, snapshot_date)` index is left as-is rather than extended to include `created_at`; same-date row counts per portfolio are small enough (at most a handful, gated by the sync cooldown) that the extra sort cost is negligible — revisit only if that assumption stops holding at real scale.

### ADR-023 — OAuth `state` parameter, server-generated and stored in Redis, single-use
**Date:** 2026-07-25
**Decision:** `broker_connection_service.init_connection` now generates a random `state` token (`secrets.token_urlsafe(32)`), stores it in Redis keyed to the requesting user and broker (10-minute TTL), and passes it to the adapter's `get_login_url`. `handle_callback` requires `state` back from the frontend, verifies it against what's stored (matching both user and broker), and deletes it — single-use, per the OAuth2 `state` convention. Noted as a gap during Milestone 4b's broker-connect work (`UpstoxAdapter.get_login_url` sent no `state` at all) and implemented now as part of the Phase 1 cleanup pass.
**Reasoning:** Without `state`, the callback endpoint had no way to verify the redirect it received actually corresponds to a connect attempt *this* user initiated — a crafted or replayed callback request (same auth-code-exchange shape) could be pointed at a different user's session. `state` is the standard OAuth2 answer to exactly this: a value the client controls, the broker echoes back unchanged, and the server checks before trusting the rest of the request. Storing it in Redis (rather than, say, a signed cookie) reuses infrastructure already in this codebase (`discovery_service`'s cache) and keeps the check entirely server-side.
**Alternatives considered:** A signed, httpOnly cookie carrying the state, checked by the browser round-trip — rejected as unnecessary complexity given the callback already goes through a JWT-authenticated endpoint; Redis with a short TTL is simpler and just as effective here, since the identity check (does this state belong to this JWT-authenticated user) doesn't need a second independent channel. No `state` at all, relying only on the JWT to authenticate the callback — rejected because that only proves *a* valid user is calling the endpoint, not that *this specific* connect attempt was the one they initiated.
**Consequences:** `BrokerAdapter.get_login_url` and `UpstoxAdapter.get_login_url` both gained a required `state` parameter — a breaking signature change, but there's exactly one adapter implemented so far (ADR-012), so no other call sites needed updating beyond tests. `POST /broker-connections/callback` now requires a `state` field in its request body (additive to the request shape, not the response); `app/broker-callback/page.tsx` reads it from the broker's redirect query string alongside `code`.

### ADR-026 — Portfolio comparison is a single `GET .../compare?ids=a,b`, computed on read, no new table
**Date:** 2026-07-26
**Decision:** Milestone 6 adds `GET /api/v1/portfolios/compare?ids=<uuid>,<uuid>` — a comma-separated pair of portfolio ids in a query string, on a plain `GET`. `portfolio_comparison_service.compare()` fans out to the already-existing `portfolio_profile_service.get_detail`/`get_analytics_view` for each id (each already enforces visibility via `get_visible_portfolio`) and to three new pure diff functions in `analytics_service.py`, then assembles a plain dict — no new marshmallow schema, no new database table.
**Reasoning:** Comparison is entirely derived from data that already exists (`Portfolio`/`Holding`/`PortfolioSnapshot`) and needs no persistence of its own — there's nothing to store beyond what a sync already produces. A `GET` keeps a pure read cacheable and bookmarkable/shareable as a URL, which a `POST` with a JSON body wouldn't be. A query-param pair reads as "a filter over the portfolios collection" — in the same spirit as discovery's filterable query params — without inventing a new URL shape (`/compare/:a/:b`) for the one endpoint that needs it.
**Alternatives considered:** Two path segments (`GET /portfolios/:a/compare/:b`) — rejected as asymmetric-looking for an inherently symmetric pairing (it reads as "compare b against a," not "compare these two"), and it doesn't obviously extend if comparing more than two portfolios is ever wanted (unlikely, per product-requirements.md's two-portfolio scope, but a query-param list degrades more gracefully than an ever-growing path). A `POST` with `{"portfolio_ids": [...]}` — rejected; nothing about this request needs a body, and a `GET` is simpler to test, cache, and link to directly.
**Consequences:** `ids` must currently contain exactly two ids (enforced in the route, `400 VALIDATION_ERROR` otherwise) — extending to more than two portfolios later, if ever needed, would be an additive relaxation of that check, not a breaking change to the URL shape. No migration was needed for this milestone.

### ADR-027 — Milestone 6 ships link-only entry into `/compare`, not a dedicated portfolio picker
**Date:** 2026-07-26
**Decision:** The only ways into the frontend's `/compare` page this milestone are contextual links that already carry both portfolio ids — a "Compare with mine" link on `InvestorCard` (Discovery Feed and Public Investor Library) and on the portfolio detail page (`app/portfolios/[id]/page.tsx`), both only shown when the viewer has their own portfolio and isn't looking at it. Navigating to `/compare` without two distinct ids in the query string shows the existing `EmptyState` component with a link to `/discover`, not a search/picker UI.
**Reasoning:** Milestone 6's stated scope is "compare two portfolios / shared comparison components / diff visualizations" — no picker was requested, and every entry point identified during planning already has both ids at hand at the moment of the click (the viewer's own portfolio id via `useMyPortfolio`, the target's id already rendered on the card/page being viewed). Building a dedicated picker (two searchable lists over discovery + library) would be real net-new UI surface raising its own unresolved questions (pagination inside a picker? search across an unbounded feed?) that were never part of what was asked for.
**Alternatives considered:** A dedicated `/compare` picker page with two investor-search inputs — rejected for this milestone as scope the request didn't ask for; the backend endpoint already accepts any two accessible ids regardless, so this is purely a frontend addition that can be layered on later with zero backend change if the `/compare` empty state turns out to be hit often.
**Consequences:** A user can't reach `/compare` cold, without first visiting some other page — an intentional, documented limitation, not an oversight, so a future reader of the empty state doesn't have to guess. Revisit only if the empty state is hit often enough in practice to justify building a picker.

### ADR-028 — Rules-based auto-categorization scoped to 3 of 8 strategy categories; Growth/Value/Dividend/ETF/Long-term deferred
**Date:** 2026-07-26
**Decision:** Milestone 7's `strategy_categorization_service.py` auto-assigns only **Small-cap Specialist** (market-cap allocation majority, threshold `> 50%`), **Low-risk** (annualized volatility `<= 15%`), and **Momentum** (trailing ~90-day value-weighted return `>= 10%`) — reusing `analytics_service`'s existing market-cap allocation and volatility computations, plus a new `compute_portfolio_momentum` that reuses the exact same per-holding historical-closes fetch already pulled for volatility (ADR-024), no new broker API calls. Recomputed every sync (`sync_service.run_sync`), delete-and-reinsert, same idempotent pattern already used for `Holding` rows. **Growth, Value, Dividend, ETF, and Long-term are explicitly not auto-assigned this milestone.**
**Reasoning:** Growth ("expanding revenue/earnings quickly"), Value ("priced below intrinsic worth"), and Dividend ("steady dividend-paying") all need fundamentals/valuation/dividend data that no part of this codebase ingests anywhere — the same class of gap ADR-008 identified for volatility before Milestone 5 resolved it, except here there's no Milestone 5-equivalent data source in view yet. ETF needs an instrument-type field distinguishing an ETF from a stock, which doesn't exist — `analytics_service.py`'s own docstring already notes every holding synced so far is equity. Long-term ("holds positions for years, not quarters") is the closest call: a cross-snapshot sector-allocation-stability signal is theoretically computable from `PortfolioSnapshot` history (kept append-only per ADR-025), but there's no validated stability-and-duration threshold to use yet without real production sync history to calibrate against — shipping a guessed threshold here would be exactly the "looks precise but isn't verified" gap this product's own principles (ADR-008, `app/data/sector_mapping.py`'s own docstring) warn against.
**Alternatives considered:** Auto-assigning all 8 with best-effort heuristics (e.g., proxying Value/Growth off sector composition, proxying Long-term off `portfolio_age_days` alone) — rejected. `portfolio_age_days` is explicitly documented elsewhere (`compute_portfolio_age_days`'s docstring) as "time-since-Nexarch-started-tracking, NOT true holding-acquisition date," so using it alone for "Long-term" would silently misrepresent what's actually known. A single overall "confidence score" per category instead of per-category explanation text — rejected per ADR-007's no-composite-score precedent; a labeled, transparent threshold-and-observed-value sentence keeps every claim individually checkable.
**Consequences:** All 8 categories remain in the fixed taxonomy and remain filterable in the Discovery Feed — Public Investor Library entries can still be manually tagged with any of the 8 (unaffected by this ADR). Only verified portfolios are affected, and only 3 of 8 categories can ever appear on one automatically. The three thresholds (`0.5`, `0.15`, `0.10`) are provisional, chosen from general market conventions (Nifty 50's own long-run annualized volatility band, a materially-strong quarterly move) rather than calibrated against Nexarch's own production sync history, which doesn't exist yet at meaningful scale — same "revisit once there's real data" caveat ADR-024 already carries for volatility itself. Growth/Value/Dividend/ETF/Long-term should be revisited only once a genuine new data source (fundamentals/valuation vendor, dividend data, instrument-type classification, or a validated stability threshold) makes them honestly computable — not before.
